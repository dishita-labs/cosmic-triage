## Decisions made (non-obvious, unilateral)

1. **`parent_candid` taken literally.** ALeRCE attributes a prv detection to a *later* delivering alert than the first packet that carried it (e.g. ZTF25aankqhe's 60780.36 detection → alert 60805.31, although the 60785.33 alert is inside its 30-day window). The literal rule is conservative (cannot leak, may drop known data). Measured cost: 197 / 272 prv detections. → Needs architecture decision 3.
2. **30-day bound on non-detection delivery** (`packet_history_days: 30`) — the parenthetical justification of the rule made explicit; stricter than "[nd.mjd, t]" alone.
3. **Per-alert fields used for count and span as well as first detection** (max of known vs packet values), mirroring the BTS filter's `ndethist` / `jd − jdstarthist` use. The approval says "used in the pre-filter" without detail.
4. **Allow-list is source-scoped** (Fink alert rows only); ALeRCE records with the same names are still scrubbed (fixture v).
5. **"Positive subtraction" means explicitly positive** for labels (`isdiffpos` missing ⇒ not qualifying).
6. **Recall denominator** from BTS + ALeRCE `firstmjd` (not from our superset, which would hide superset misses). Outside-superset objects are attributed to the superset conditions; their extra at-t evaluation is ALeRCE-only (labelled), so the diagnostic does not depend on Fink.
7. **Audit sample** drawn from unique contaminant objects (not object-nights); blind form; Sherlock offset else ALeRCE `distnr` for the offset stratum.
8. **Known-asteroid check** via ALeRCE's public `ss_ztf` (alert-packet `ssdistnr`), diagnostic and stratification only — no pre-filter change.
9. **Lasair batched prefetch** (`LasairClient.prefetch`): one IN-query per 100 objects writes the exact per-object cache entries the single-object calls read (unit-tested). 57 of 162 pool objects are absent from Lasair altogether (verified live for one).
10. **Fink outage** (≈ 14:47–16:54 IST, again from ≈ 17:05): the refetch was stopped rather than retried blindly and resumed when Fink answered (4,040 objects, 0 errors).

## Needs architecture decision

1. **Per-alert `i:jdstarthist` rejects real supernovae with old pixel history (§14.3 pre-filter).** ZTF's `jdstarthist` counts any ≥ 3σ detection at the pixel since survey start, so host-nucleus residuals or an earlier unrelated transient set it years back. Cost on the same denominator: bright recall 74.8% → 59.4%; 10 object-nights (4 objects incl. two BTS SNe Ia and one SN II) from histories 53–2,204 d old, 12 from the window edge. Options for Fable: (a) keep as is; (b) use `i:jdstarthist` for the window only when contiguous with the current episode (e.g. ≤ 30 d before the first known detection), and route older history to a `prior_flares` signal instead of rejection; (c) use the per-alert fields for the count/30-min span only (as the BTS filter does), not for the 14-day window.
2. **Known asteroids are not rejected by the pre-filter (§14.3).** 28 / 50 contaminants (56%) and 20–26 of the 46–55 nightly "bright SN-like" members match a numbered asteroid at 0″ in the alert packet. They inflate contaminant counts and the budget-binding count (median 51 → 27 without them). Proposal: add a time-honest alert-packet rule (reject when `ssdistnr` ≤ ~12″ and `ssmagnr` set, as BTS-style filters do), source: Fink `i:ssdistnr` (needs one more column refetch) or ALeRCE `ss_ztf`.
3. **`parent_candid` attribution is late (§14.1 Snapshot semantics).** Literal rule excludes 197 / 272 prv detections at t. A time-honest alternative mirroring the non-detection rule: a prv detection is known at t if some stamped alert of the object with mjd in [d.mjd, min(t, d.mjd + 30 d)] exists (the packet history rule). Note that a prv detection can only appear in packets after it, so the alternative cannot introduce post-t data; the residual risk is a packet that did not carry it (different field/readout channel).
4. *(Informational)* 7 BTS bright objects are excluded at the superset stage because every PS1 row is star-like; the approved star-counterpart rule drops them. No action proposed.

## Learning checkpoint 1.1 (for the owner)

- *Why "delivered by an alert ≤ t" is the right definition of knowledge:* at t a broker only holds packets that have arrived; a detection that sits in the archive with mjd ≤ t but only reached anyone inside a later packet's history was not knowable at t. Timestamp-of-observation and timestamp-of-knowledge differ; replay must use the latter.
- *Why per-alert fields are honest but object-level ones are not:* `i:jdstarthist` in a packet with jd ≤ t is what ZTF told everyone at that moment; a broker's object-level `jdstarthist` is recomputed over everything it holds *now* (including later packets), so it encodes the future.
- *How a contaminant label could be wrong, and what evidence would change it:* a never-saved bright object can still be a real SN that BTS missed (hostless, poor visibility, busy night). The audit will show it as SN-like (rise/fall over weeks, host offset, later TNS classification). The asteroid finding shows the opposite failure: labels that are "right" (not SNe) but for objects that should never have entered the pool.
