## What was built

- `ingest/alerce_db.py`: queries ALeRCE's public read-only PostgreSQL for the forward-pool superset. The credentials are the ones ALeRCE publishes for public use; they are fetched at query time and never stored. Results are cached, so offline rebuilds never touch the database.
- `replay/pool.py`: `ForwardPool` works in two stages:
  1. A **superset** of necessary conditions only. Each is either monotone over the object's history (first alert in the window, final `ndet` ≥ 2, all-time brightest ≤ 19) or static context (|b|, star-like PS1 counterpart in *every* crossmatch row).
  2. The **time-honest pre-filter** `evaluate(raw, t)`, computed only from records with `mjd ≤ t` after denylist scrubbing.

  Hydration is ALeRCE light curves plus Fink alert rows (score columns only).
- `replay/denylist.py` + `configs/replay/denylist.yaml`: denylisted fields (including `peak*`, `v:*` and `d:lc_features*`) are dropped from every raw record before any processing.
- `replay/clock.py`: `Clock.snapshot(t, pool) → Snapshot`. Counts, brightest and latest magnitude, first and last detection, and position are all recomputed from data ≤ t.
- `replay/labels.py` + `configs/replay/class_map.yaml`: the §6.4 label rules, with BTS type mapped to coarse K.
- `schedule/visibility.py` and `replay/theater.py`: astropy night edges, Sun/Moon tracks with Moon illumination, and alt/az grids. `NightFrame`s are computed at 5-minute cadence, from sunset − 30 min to sunrise + 30 min, about 144 per night.
- `scripts/run_m1_spine.py`: a deterministic run (`run_id` = config hash + seed + nights) that writes Snapshots, pool summaries, Theater frames, `manifest.json` (seed, per-config hashes, code version, model ids = none, tokens/USD = 0, output hash) and a span JSONL under `runs/bench/2025-04-19/`. Two offline runs give the identical output hash `ef006c81…`.
- `api/app.py` (FastAPI, presentation only): `/api/runs`, `/api/runs/{run}/nights/{night}/candidates[/{oid}]`, `/theater/nights`, `/theater/{run}/{night}/frames`, `/theater/{run}/{night}/events` (empty in S0).
- `console/` (Vite + React + TS, Plotly; types generated from pydantic via JSON Schema → `json-schema-to-typescript`):
  - **Night Theater S0**: a zenith-centred alt-az dome (N up, E left) with horizon, cardinal points and altitude rings; a dashed facility-limit ring read from config; sky colour and twilight glow driven by the backend Sun altitude; the Moon drawn with its astropy illuminated fraction; candidate markers sized by latest real magnitude; faint altitude tracks for all candidates and a highlighted track with hour ticks for the selected one; a time-cursor scrubber with twilight bands and sunset/dusk/dawn/sunrise marks; play/pause/speed controls, keyboard shortcuts (space, ←/→, shift, F, L, Esc) and full screen.
  - Sizes are vmin-based, verified with a headless-Chrome screenshot at 3840×2160.
  - The persistent legend states "Telescope and its observations are simulated; sky, candidates, detections, and reports are real", with L0/L1 badges and a "model prediction — from M3" key. Bench runs show `run_id` and `config_hash`; exploratory runs get an `EXPLORATORY` watermark. The frontend only projects alt/az and interpolates between frames; it does no astronomy.
  - **Candidates**: a sortable pool table and a light curve showing detections with errors and 5σ upper limits, a `t (decision time)` marker, and a time cursor that replays how the light curve grew. Hash routing `#candidates/<oid>`.
- Tests (179 offline, sockets blocked): 26 data-driven leakage fixtures plus a full Clock-path test; tests for superset logic, label rules, visibility/frames versus direct astropy, frame determinism, the API over a synthetic run, and import boundaries (including a test that injects a violation and expects import-linter to catch it). The fast Galactic-latitude function is checked against astropy to 1e-6°.

## Decisions made (non-obvious, unilateral)

1. **Lasair rejected as the pool superset source** after measurement. Lasair's `objects` aggregates (`jdmin`, `ncand`, `maggmin`) cover a rolling recent window, not the full history. For example, ZTF25aaizxrf shows `jdmin` in late May and `maggmin` 20.9 although it was discovered in mid-March at 17.3, so they are not monotone and silently dropped real pool members. I replaced them with ALeRCE's database, whose `magstat` is full-history. This keeps the architecture's pool source (ALeRCE) and does not change the pre-filter.
2. **Pre-filter reading of "≥ 2 detections ≥ 30 min apart, drb ≥ 0.5"** (config values unchanged). The *alert* must pass drb ≥ 0.5 and m ≤ 19, while the detection count and time span come from the position's positive detection history ≤ t. This mirrors BTS's alert filter (`ndethist`, `jd − jdstarthist`). The first implementation required drb on every counted detection, but prv_candidates history detections carry no drb in ALeRCE's record. That cost recall: BTS-saved-by-t objects reaching the pool rose from ~70% to ~78% after the change. I made the change before any comparison and covered it with two new fixtures.
3. **Pre-filter details:** a star-like counterpart means sgscore1 ≥ 0.5 within 2″. A bright star means a PS1 (`srmag1`) or Gaia (`maggaia`) source brighter than 15 mag within 20″; only the nearest source is available. |b| ≥ 7°. Static context comes from the first Fink alert ≤ t, falling back to the superset's PS1 fields.
4. **M1 nights are 2025-04-19 to 04-23, not 04-01 to 04-05.** ZTF recorded no alerts from 2025-03-31 to 04-04 (zero new objects in ALeRCE; zero Fink alerts on 04-01 and 04-03). These are the first five consecutive spring-2025 nights with continuous coverage.
5. **Decision time** t = 20:00 UTC on the night's local calendar date (about 13:00 PDT): after the previous night's data and before sunset.
6. **"First detection"** = the earliest detection ≤ t in ALeRCE's light curve, which includes prv_candidates history. The object-level `mjdstarthist` is denylisted as a final aggregate.
7. **Position** = circular mean of detections ≤ t, not ALeRCE `meanra`/`meandec`, which average over future detections.
8. **Bright SN-like** (the KT #4 definition, also used in pool stats) = brightest qualifying magnitude at t ≤ 18.5 and the latest alert-time Fink SIMBAD crossmatch is not stellar/AGN. In practice the PS1 star cut already removes stellar matches, so bright and bright SN-like coincide.
9. **Labels:** "bright" for never-saved objects uses the full-history brightest positive detection (replay-only, never in a Snapshot). Coarse classes map IIb, Ibn, Icn and Ca-rich to Ibc. Unmapped types (for example `Other`) get no coarse class.
10. **The Snapshot carries Fink's alert-time `d:tns`** as `tns_alert_time`, from rows ≤ t only. The architecture names it as an alert-time flag (§2.2, KT #2), and the data show it is time-varying (`''` → class after the TNS report).
11. **Artifacts** go to `runs/bench/<first night>/<run_id>/` plus `runs/bench/<first night>/<run_id>.jsonl`. They are labelled `bench` because they come from the rigorous track and involve no LLM; they contain no benchmark numbers. Output hashes exclude wall-clock span latencies.
12. **astropy IERS auto-download is disabled** (`iers.conf.auto_download = False`) for determinism and no hidden network; the alt/az effect is sub-arcsecond.
13. **Galactic latitude** uses astropy's ICRS→Galactic matrix, derived once, instead of a per-object `SkyCoord` (about 1000× faster; tested equal to 1e-6°).
14. **Theater S0 scope:** no star catalogue, Milky Way or Aladin (those are S3), no pointing or detections-in-time (S1), and no Investigator events (S2). `belief_top` and `expected_reward` are `None` until M3. The facility is shown idle with an L1 badge.
15. **TheaterNight gained additive optional fields** `min_altitude_deg` and `site_timezone`; the schema snapshot was refreshed intentionally.
16. **ALeRCE rate limiting:** one hydration pass hit HTTP 429 on 12 objects. The client now retries up to 7 times with jittered backoff, and builds use 4 workers.

## Known limitations (reported, not fixed)

- **Pre-filter recall vs BTS:** 38–43 of 51–55 objects that BTS saved by t, with first detection inside the window, reach the pool each night (about 78%). Most misses had a brightest magnitude at t of 19.1–19.7, which is above the specified m ≤ 19 cut (BTS scanners save some candidates beyond its strict filter). Changing the cut is a §14.3 decision.
- **Contaminant share:** about 38 of roughly 100 pool members per night are "never saved & filter-passing & bright", i.e. contaminants under §6.4's rule. That is a large fraction of the pool and worth Fable's attention when the label rule is used for metrics.
- The 14-day window means early-night pools can include objects whose light curves are already declining. This is by design.

## Needs architecture decision

1. **KT #1 fallback (carried over from M0, §14.7):** only applies if TNS bot credentials cannot be obtained. See `runs/reports/M0.md`.
2. **Old objects appearing as "new" (§14.1, denylist):** 2–6 of about 100 pool members per night have pre-2025 designations (for example `ZTF18aawhrjb` and `ZTF23absjmpv`). Their earliest detection in ALeRCE's light curve falls inside the 14-day window, while ZTF's own history (`jdstarthist`) says otherwise.
   - The time-honest fix is the **per-alert** `jdstarthist` in Fink alert rows ≤ t, which is known at alert time. But `jdstarthist` is on the denylist (I added it to block ALeRCE's *final* object-level value), and changing the denylist is a §14.1 trigger.
   - Question: may per-alert `i:jdstarthist` from rows ≤ t be allowed, so first detection = min(detections ≤ t, alert-time jdstarthist), while the object-level final value stays denylisted? Until decided, these objects stay in the pool.
3. **Contaminant label volume:** is ~38% contaminant (never-saved & filter-passing & bright) consistent with Fable's expectation from the BTS II audit? If not, should the "bright" test for never-saved objects use the same peak definition as BTS? It currently uses the full-history brightest ALeRCE detection. I did not change the label rules (§14.3).

## How to run

```
uv sync
uv run pytest                                  # offline, 179 tests
uv run python scripts/accept_M1.py             # needs data/cache (built by build_pool.py) and console/node_modules
uv run python scripts/run_m1_spine.py --offline
uv run uvicorn cosmic_triage.api.app:app --port 8000
cd console && npm install && npm run dev       # http://127.0.0.1:5173  (#theater, #candidates/<oid>)
```

`data/cache/` (about 21.8k cached responses, 182 MB) is git-ignored. Rebuild it online with `uv run python scripts/build_pool.py` (about 30–40 min; ALeRCE, Fink and the public ALeRCE DB need no credentials). The committed `runs/bench/…` artifacts let the console and API run without the cache.
